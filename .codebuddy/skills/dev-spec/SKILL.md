# 单文件开发规格

## 1. `write` 模式：创建规格

### 目的

把需求转换为一份可由后续 AI 或工程师执行的单文件技术开发规格，减少重新理解成本。

唯一交付物是开发规格文档。不得实现业务代码、安装依赖、提交变更或自动进入 `run` 模式。

### 输入与输出

需要：

- 需求文档、原型说明或用户已确认的需求陈述。
- 相关仓库上下文。

#### 定位目标仓库

按以下顺序确定 `<project-root>`：

1. 用户明确指定的目标目录或仓库。
2. 需求来源或当前任务文件所属的仓库根目录。
3. 当前工作区中唯一能够由项目文件证明的仓库。

如果存在多个候选、需求跨多个仓库，或当前目录不能证明归属，先询问用户。不得根据固定文件夹名称猜测目标，也不得默认把工作区根目录当作目标仓库。需求跨多个仓库时默认按仓库拆成多份规格分别追踪（呼应"一份 spec = 一个竖切"）；用户明确要求合并时，必须在规格中标明各仓库各自的行为与验收，不得静默共用一套。

确定后，规格中的文件路径默认相对于 `<project-root>` 表达；跨仓库依赖必须单独标明仓库和边界。

#### 与变更规格的选择

- 只需要一次性技术方案、任务拆解或跨人员交接时，继续使用本 Skill。
- 从零开始的新能力需要维护"当前系统行为"和"本次拟议变化"，或需要后续同步、归档时，使用 `openspec-mini`。
- 用户已经指定输出形式时遵守用户选择；不能同时为同一需求维护内容重复的 `dev-spec/v1` 和 OpenSpec 式变更包。

默认输出：

```text
<project-root>/dev-specs/<feature-name>.md
```

使用简短 kebab-case 功能名，并将 `<project-root>` 替换为本次确认的实际目标。不得覆盖无关文档；只有用户明确指向同一功能时才更新已有文件。

写入前完整读取 `assets/dev-spec-template.md` 并使用其章节顺序。确实不适用的内容写"无"，不得为了填满模板而编造信息。

### 结构化执行协议

当前 Skill 负责生成结构化单文件规格，`run` 模式可以执行该规格，也可以执行用户指定的其他技术文档或 `openspec-mini` 活动变更包。

为使本 Skill 产出的规格能够稳定续跑：

- 文档协议标记为 `dev-spec/v1`。
- 需求使用稳定编号 `FR-XX`，验收使用 `AC-XX`。
- 开发任务使用稳定编号 `TASK-XX`。
- 新文档中的任务状态只能是 `Pending` 或 `Blocked`；`run` 模式执行时可更新为 `In Progress`、`Done` 或 `Blocked`。
- 每项任务必须包含覆盖需求、依赖、预计文件、工作内容、完成条件和验证方式。
- 不把仍有阻塞决策的任务写成可直接执行。
- `write` 模式不把任务状态改为 `In Progress` 或 `Done`。

### 工作流程

#### 1. 确认来源与决策权

完整读取需求来源，记录每项要求来自哪里。用户后续确认或修正优先于原始文档。

严格区分：

- 已确认需求事实。
- 当前仓库事实。
- 假设。
- 开放决策。

歧义会导致不同用户行为、平台范围或技术方向时，先询问再写相关章节。已经确认的决定不重复开启。

#### 2. 检查相关代码上下文

只检查与功能有关的路由 / 入口、页面、组件、状态、请求层 / 服务层、类型、测试和命令。遵循现有模式，只有观察到的路径才能写成现有路径。

路径状态：

- `Existing`：仓库中已确认存在。
- `Create`：方案要求新建。
- `Candidate`：可能的位置，仍依赖开放决策。

不得把未来文件写成已经存在。

#### 3. 选型门禁

- 技术栈、组件库、构建、状态、请求、测试等尚未确认时，标记为阻塞决定，不自行选型。
- 项目地基尚未确认且会影响当前规格时，先停下来把地基决策问清（本仓库地基已定：零依赖单文件原型，见 `00-project-routing`「技术栈边界」；本技能集未复制 `project-foundation`，需要系统梳理时先问用户是否单独引入）。
- 当前规范未授权的范围（如另一端、另一服务）只作为依赖或已提供契约描述，不设计或授权其实施。

#### 4. 建立需求追踪

为功能需求分配 `FR-XX`，为验收条件分配 `AC-XX`。

每项需求映射到：

- 用户可见行为。
- 技术处理。
- 已知影响区域或文件。
- 验证方法。

一个任务可以覆盖多项需求，但任何已确认需求都不能在拆解过程中消失。

#### 5. 设计最小充分方案

只描述满足已确认范围所需的内容：

- 页面、路由 / 入口、组件、状态和请求（或对应服务端分层）变化。
- 数据流与相关接口。
- 需求涉及的加载、空、错误、禁用和权限状态。
- 依赖和实施顺序。
- 聚焦验证。

不得增加通用抽象、未来扩展点、大范围重构或无关质量工作。预计文件列表只是技术预测，不是逐文件授权。

#### 6. 拆分可执行任务

任务按依赖顺序排列。每个 `TASK-XX` 必须：

- 产生一个可独立验证的结果。
- 标明覆盖的 `FR` 和 `AC`。
- 标明前置任务或外部决定。
- 标明预计文件和工作边界。
- 定义完成条件和真实可用的验证方式。
- 在决定未确认时标记为 `Blocked`。

不写完整生产代码，不强制 TDD、提交或子代理流程。

#### 7. 写入并自检

使用正式模板创建或更新目标文档，并确认：

- 每项已确认需求均映射到技术处理和验证。
- 没有新增来源中不存在的产品行为。
- 事实、假设和开放决策没有混淆。
- 跨仓库 / 跨端没有静默合并。
- Existing、Create、Candidate 标记正确。
- TASK 依赖无明显循环。
- 名称、类型、路由和接口术语一致。
- 没有无法解释的 TBD、TODO 或占位文本。

存在阻塞决定时可以交付 `Blocked` 文档，但必须写清被阻塞章节和原因。

### 完成报告

报告：

- 文档路径。
- 覆盖的需求编号。
- 阻塞决定。
- 需要后续验证的重要假设。
- 是否具备交给 `run` 模式执行的条件。

不得开始实现。

## 2. `run` 模式：执行规格

### 目的

读取用户明确指定的技术文档，提取可执行范围和顺序，完成其中已确定的修改，并保留可继续执行的状态与证据。

技术文档可以是技术设计、开发方案、实施说明、任务清单、`dev-spec/v1`，也可以是 `openspec/changes/<change-id>/` 活动变更包，不要求固定模板、编号或状态字段。调用本模式只授权文档已确定范围内的常规、低风险实施，不授权扩大产品范围、擅自选型、跨仓库修改、提交代码、创建分支或自动调用其他 Skill。

### 读取输入

开始前：

1. 确认用户明确要求执行哪份文档或哪个活动变更目录；输入可以来自工作区文件、用户粘贴内容或用户提供的可读取来源。
2. 完整读取文档及其直接引用的必要内容，区分已确定要求、候选方案、开放问题和背景说明。
3. 检查相关代码、当前项目命令和工作区已有改动，确认文档描述没有被当前事实推翻。
4. 确认下一步的目标、边界、依赖和完成判断足够明确。

用户要求"按这份文档执行"表示可以实施文档中已经确定的内容，但不表示文档里的候选项、备选方案、TBD、示例或原因猜测已经获得确认。会改变实现结果的内容仍不明确时，先澄清。

### 选择执行模式

#### OpenSpec 式活动变更包

用户指定 `openspec/changes/<change-id>/`、其中的 `tasks.md`，或明确要求实施某个活动 Change 时：

1. 完整读取 `proposal.md`、相关 delta specs、`design.md`、`tasks.md`，以及理解变化所需的当前 `openspec/specs/`。
2. 用 proposal 和 delta specs 确定产品目标与行为，用 design 确定已确认技术处理，用 tasks 确定执行顺序；用户最新明确决定优先。
3. 产物互相矛盾、Requirement 没有任务覆盖、design 含 Candidate/Blocked 决定或任务无法追溯时，停止并要求先使用 `openspec-mini update` 修正规格。
4. 沿用变更包中的 TASK 编号、依赖、状态和执行记录；项目 schema 有不同约定时以项目协议为准。
5. 实施过程中只更新允许维护的活动变更状态、任务状态、实际文件、验证证据和偏差，不修改当前 `openspec/specs/`，不执行 sync 或 archive。

活动变更包是实施权威范围，但不扩大用户权限；跨仓库、依赖安装和未确认选型仍需单独授权。

#### 文档自带任务协议

文档已有任务编号、依赖、状态或执行记录时，沿用原有协议，不强制转换成 `dev-spec/v1`。

- 保留原编号和状态名称。
- 按文档依赖顺序选择下一项可执行任务。
- 文档允许维护状态时，开始、完成或阻塞后回写对应状态和证据。
- `dev-spec/v1` 使用其 `TASK-XX` 及 Pending / In Progress / Done / Blocked 约定。

#### 普通技术文档

文档没有任务协议时，在执行过程中建立简短的临时清单：

- 使用 `RUN-01`、`RUN-02` 等临时编号。
- 每项记录目标、依赖、影响区域、完成条件和验证方式。
- 同一时间只执行一项，内部状态使用 Pending / In Progress / Done / Blocked。
- 默认只在过程与完成报告中维护清单，不为了执行而改写原技术文档；用户明确要求记录回文档时再写入。

临时清单只是执行索引，不得增加原文档没有的产品行为或技术决定。

### 执行流程

#### 1. 建立执行基线

记录文档来源、目标仓库、文档中已确定的范围、当前任务或临时清单、前置依赖和阻塞项。目标仓库不明确且多个候选会改不同文件时，先确认再动手，不默认。保留用户已有改动，不覆盖、不回退，也不把无关变化算入本次结果。

文档包含当前规范未授权范围的内容时（如另一服务、另一端），只执行已授权部分；未授权部分作为前置条件记录。

#### 2. 复核下一项工作

开始每项工作前确认：

- 需求和技术处理已经确定。
- 前置任务和外部依赖已经满足。
- 当前仓库事实与文档没有实质冲突。
- 不需要未经确认的新依赖、脚手架、组件库或核心架构决定。

缺少项目地基且会影响实施时，停止并要求先确认地基（本仓库地基为既成事实，见 `00-project-routing`）。出现新的技术选择时遵守 `tech-gate`，不能把推荐或候选当作项目事实。

#### 3. 处理文档与现实偏差

文档中的预计文件和结构属于实施预测。发现差异时：

- 实际路径不同，但用户行为、验收、技术方案和影响范围不变：说明原因，按最小范围继续并记录实际文件。
- 会改变用户行为、验收条件、平台、公共接口、技术方案或仓库边界：停止并请用户确认。
- 文档与当前代码或其他有效约束冲突：记录证据并标记阻塞，不得为迁就实现而改写文档要求。

#### 4. 实施最小修改

将当前工作标记为进行中，只实现其完成条件需要的变化，并遵守项目既有模式与适用 Rule。

不得加入未来扩展、无关重构、依赖升级、额外平台适配或文档中没有的产品行为。预计文件列表不是扩大修改范围的授权。

#### 5. 验证结果

优先采用文档指定且当前仓库真实存在的验证方法；文档未指定时，使用与改动风险相称的现有检查和必要手工场景。

- 不存在命令时记录"当前未配置"，不得发明命令。
- UIUE 相关工作记录实际对照的页面、状态、分辨率或断点及差异；移动端的改动还要记录验证的端（iOS / Android）与载体（模拟器 / 真机），未验证的端如实标注。
- 服务端改动记录实际执行的请求 / 场景和结果，未覆盖的路径如实标注。
- 静态阅读不能证明运行、交互、像素还原、动画、焦点或网络时序已经通过。
- 同一未知问题或验收项达到现行异常规则的失败阈值时停止并记录证据。

只有完成条件满足且验证证据充分时，才标记为完成；否则保持未完成或阻塞。

#### 6. 继续或停止

完成当前项后继续下一项，直到：

- 文档范围全部完成；
- 遇到阻塞决定、外部依赖、文档冲突或失败阈值；
- 用户要求停止；
- 已无可执行事项。

实现结束后询问用户是否需要 `review-change` 审查；本模式不自动调用 Review。`openspec-mini` 活动变更完成时，只报告其是否具备 sync 条件，不自动同步当前规格或归档。

### 完成报告

向用户报告：

- 执行的技术文档来源。
- 已完成、未开始和阻塞事项。
- 实际修改文件。
- 已执行检查及结果。
- 与文档的偏差、未验证项和剩余风险。
- 如果执行的是活动变更包，说明 Requirement/Scenario 覆盖情况及是否具备 `openspec-mini sync` 条件。
- 若阻塞，说明恢复前需要确认或补充什么。

只有全部事项完成且验证范围明确时才声明完成。不得自动提交、推送、创建分支或处理文档范围外问题。
