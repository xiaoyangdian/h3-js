# 审查变更

## 目的

对变更进行证据型只读审查。交付物是**固定格式的审查报告**，不是修正后的代码。以最小证据成本支撑结论，禁止与结论无关的求证。

不得修改文件、自动切换分支、安装依赖或调用其他 Skill；唯一例外是第 8 节的自动交接。用户随后要求修复时，把它视为新的实现请求。

## 评审档位（先定档，再审查）

| 档位 | 适用 | 流程 |
|---|---|---|
| 标准档 | 业务仓库的业务变更 | 完整流程：六类语义审查 + 覆盖矩阵 + 硬模板 |
| 轻量档 | 自用 / 工具项目；或用户明示"不用太严格 / 快速过一遍" | 只查会咬人的问题，轻量模板 |

档位由目标仓库性质与用户口径决定，不得自行拔高或降低；拿不准按标准档。

**轻量档规则**：

- 只查"会咬人的"：C1 底线、C2 契约、变更集自洽（审查范围内新增代码 / 配置 / 文档互相引用是否闭环——方法加了没人调、文档描述了不存在的行为、schema 与使用方不一致等）、残留扫描中的凭据与冲突标记。
- 跳过 C3 架构细节与 C5 优化；C4 只做变更集自洽一项。
- 低影响疑点（纯风格、一致性、体验类）不报也不求证，摘要一句话带过即可。
- 严重度直接定级（第 5 节），输出用轻量模板（第 7 节）。

## 耗时纪律（两档通用）

- **差异一次到位**：先看 `--stat` 评估规模。新增文件（new file）**跳过 diff 直接 Read 文件**——新增文件的 diff = 全文件内容，拉取必截断且无变更前对比价值；修改文件单个 diff 预计超 ~200 行就单独拉取，多文件预计超出单次输出上限就按文件分组分批拉取；禁止全量拉取被截断后再重拉。
- **不重复读**：diff 已包含的内容不再全量读文件；只为理解契约、调用方或既有模式所必需时才读未改动文件。
- **疑点先裁决后求证**：命中候选先判断"即使属实会不会进问题清单"——不会报的直接跳过并一句话记录，不做完整求证。
- **结论一次成型**：证据足以定论后不再重复推导；同一事实不二次验证。
- **交叉验证设上限**：主动交叉验证（如"谁调用 X"、HEAD 版本对照）标准档 ≤3 次、轻量档 ≤2 次，且仅用于支撑会进清单的发现。
- **报告只组织语言**：写报告时不重新推导、不重新审查。

## 0. 必读上下文（固定清单，不得自选）

读取目标项目的常驻规则（`.trae/rules/` 全部常驻文件；CodeBuddy / WorkBuddy 侧同一套在 `.codebuddy/rules/`）；项目没有常驻规则时读 `README.md` 与根目录说明文档（本仓库即 `交接文档.md` / `参考资料.md`，即需求基线）；两者都读不到时在「未验证内容」中记录，不得静默跳过。

变更同时触及多个仓库时，并读涉及的每个仓库的常驻规则。

## 1. 确定审查目标

优先使用用户明确提供的文件、差异、提交、分支或变更范围。

用户只说"审查我的改动"时，审查当前暂存和未暂存的变更；先识别与本次需求相关的未跟踪文件，不得静默忽略。

用户给出明确文件或差异范围时，不扩大到整个仓库。只有为理解变更契约、调用方或既有模式所必需时，才读取相关未改动文件。

## 2. 建立需求基线

读取相关需求、已确认改动清单、开发规格或变更说明，形成简短验收清单。

无法获得完整意图时，只根据差异和附近代码能证明的内容审查，并在摘要中明确"需求完整性审查受限"，不得虚构需求。

## 3. 第一遍：机械扫描（残留物，零自由度）

对本次差异的**新增行**逐条匹配下表。命中模式记为候选，先按"即使违反会不会进问题清单"快速过滤（CLI 脚本的 `console.log`、文档示例里的 localhost 等明显不报的直接跳过），再对剩余候选按判定标准裁决；判定不通过的一句话记入未验证或忽略，不做完整求证。

| 规则 | 扫描模式 | 违反判定 |
|---|---|---|
| RC-M1 | `console.log`、`debugger`、临时 `print`、调试弹窗 | 新增行出现，且不属于项目约定的日志封装或构建条件块 |
| RC-M2 | 硬编码 `localhost` / `127.0.0.1` / 临时绝对路径 / 测试账号 | 新增行出现 |
| RC-M3 | Mock / 假数据：DEV 假数据分支、写死响应、固定成功结果 | 出现即违反（项目约定 Mock 只能在指定 Mock 层；无此约定时结合变更目的裁决） |
| RC-M4 | 绕过开关：强制 `return true`、跳过权限/校验/错误处理的临时分支 | 无需求依据 |
| RC-M5 | `.only`、`fit`、`fdescribe`、`xit`、本地测试入口；Git 冲突标记、`throw new Error("TODO")`、临时 return、大段注释旧代码、不可达分支 | 出现即候选，结合变更目的裁决 |
| RC-M6 | 空捕获 `catch (e) {}`、字面量凭据（`Bearer `、`sk-`、长随机串） | 空捕获需既不抛错也不提示也不记日志；凭据出现即违反 |

## 4. 第二遍：语义审查（六类规则，按序全判）

标准档：每条规则（RC-01–12）必须逐条给出判定，不适用须写一行理由。轻量档：只全判 C1 与 C2，C4 只做变更集自洽检查，C3/C5 仅在差异中一眼可见且会咬人时报，其余无需逐类写理由。规则是检查菜单，类内仍可沿调用链、状态、请求和渲染自由追踪；发现必须引用规则 ID。

### C1 底线（正确性 + 安全，含静默失效）

| 规则 | 检查点 | 违反判定 |
|---|---|---|
| RC-01 | 空值/空索引访问：无守卫的属性链、数组方法调用 | 正常数据即可触发 |
| RC-02 | 异步与生命周期：未 await、连续请求互相覆盖、异步响应覆盖用户已修改的本地状态（加载/保存返回时对本地状态整表回填且无守卫——如无条件 `Object.assign`、加载完成前交互未禁用、无请求序号守卫）、监听器/定时器/订阅/连接未在卸载或关闭时清理 | 有实际错序或累积后果 |
| RC-03 | 静默失效：失败被吞、兜底伪装成功（空列表不报错、缺失字段渲染成有效值、错误响应被当作正常返回） | 用户看到"正常"但数据错或空 |
| RC-04 | 安全：前端危险注入面（v-html / innerHTML / dangerouslySetInnerHTML）未消毒、后端拼接 SQL / 命令 / 路径未参数化、明文凭据、越权展示 | 出现即候选 |

### C2 契约一致性

| 规则 | 检查点 | 违反判定 |
|---|---|---|
| RC-05 | 接口口径：URL、字段名、枚举值、分页 / 响应结构 vs 已联调契约或 Mock 层 | 与已确认契约不符；未联调且已标注的不算 |
| RC-06 | 类型与解包真实性：类型声明、注释与请求层 / 数据访问层实际解包行为不符（死类型、自造响应外壳） | 有代码引用或会误导联调 |

### C3 架构与规范

| 规则 | 检查点 | 违反判定 |
|---|---|---|
| RC-07 | 目录与归属：文件在项目约定目录；分层职责不越界（UI / 页面层只管展示与交互状态，业务逻辑在业务层 / 服务层 / composable / hook 等项目约定的业务承载层） | 偏离常驻规则或项目架构文档约定 |
| RC-08 | 模式一致：命名、常量替代 magic string、与既有代码模式一致 | 与仓库已确立模式冲突（如未复用已收拢的封装组件、绕开既有模式自写同构实现）——属现状问题，必报 |

### C4 治理合规

| 规则 | 检查点 | 违反判定 |
|---|---|---|
| RC-09 | 范围与需求：基线验收项缺失；疑似误加的无关改动（临时/调试残留、无说明的附带删除） | 验收项缺失；无关改动无法归因到需求基线**且疑似误加**。混合提交里多个功能正常但相互独立的修改属正常做法，**只建议分开、不定级、不进问题清单**（摘要一句话即可）；怎么拆提交由用户自己决定 |
| RC-10 | 技术门禁：新增依赖、构建配置改动是否已过 tech-gate 确认留档 | 无留档依据 |

### C5 优化

| 规则 | 检查点 | 违反判定 |
|---|---|---|
| RC-11 | 性能与反馈：全量引入、重复请求；加载/空/错误/禁用态缺失（含首屏闪空态：列表初始为空 + 请求在途 + 空态渲染未区分 loading）、占位操作无反馈 | 有可感知影响 |
| RC-12 | 可维护性：重复块（按下方重复度检测细则）、过长函数、误导命名 | 重复块按细则判定；其余有实际影响才报 |

**RC-12 重复度检测细则（封装候选）**——对本次差异的**新增行**做块级重复比对，分两步执行：

- **第一步·枚举留痕**：先机械枚举本次新增行中全部骨架相同或近似相同（变量名 / 文案 / 属性值不同、结构一致）的代码块——模板段（含 SVG / JSX）、样式段、配置对象、SQL / schema 段、工具函数——满足"出现 **≥2 次** 且单块 **≥10 行**（SVG / 内联模板段放宽到 ≥8 行）"的候选块**全部列出**；结论为"无候选"也要在摘要写一行。禁止只报想起来的部分。
- **第二步·逐个裁决**：对枚举清单逐个按排除规则裁决，命中排除项的不报：语法要求的必要重复；连续单行元素的内容巧合相似（如两个各一行的 input）；既有代码中已存在的重复（不在本次新增范围，摘要一句话记录，不进清单）。
- 报告要求：标题写「XX 重复 N 次（单块约 M 行），建议封装为 XX」；最小修正方向给一行签名草案（组件 props/emits 或函数入参出参）；严重度按矩阵「仅未来风险或一致性 × 体验/维护」= P3，重复 ≥3 次或累计 ≥60 行时在最小修正方向注明"建议本次处理"。
- 锚定例证：三个密码输入框各内联一份开/合眼睛 SVG（单份约 40 行、累计约 120 行），实现时未报、事后才补封装——此后此类必须报「输入框组件封装候选」。

C6 残留 = 第一遍机械扫描结果，不再语义重查。

## 5. 严重度定级（先定级，再写报告）

P0 不进表格，命中即判：可利用注入、明文凭据泄漏、越权展示。

轻量档不走矩阵：P0 直判保留，其余按"触发条件 × 实际影响"一句话理由直接定 P1/P2/P3，理由写进发现。

标准档按两因子矩阵定级（行=触发条件，列=实际影响）：

| 触发 \ 影响 | 数据错误或核心功能失效 | 局部功能退化 | 体验 / 维护 |
|---|---|---|---|
| 默认或必然路径 | P1 | P2 | P3 |
| 特定条件可触发 | P2 | P2 | P3 |
| 仅未来风险或一致性 | P3 | P3 | 不报 |

矩阵"仅未来风险或一致性"行**不适用于已确认的 RC-08 违反**：与仓库已确立模式冲突（如组件乱用、绕开已收拢的封装自写同构实现）是当下的现状问题，按"特定条件可触发 × 体验/维护"定 P3 必报；该行只收无既定模式可依的纯偏好类差异（如两种均可接受的写法选择）。

本规则集锚定例证（示例，供定级校准）：

- P1：死类型与请求层真实解包口径冲突、会误导联调；核心列表页静默取不到数据。
- P2：缺失字段兜底渲染成"启用"；分页字段名未对齐导致联调后表格空白。
- P3：文档口径不一致；占位按钮无反馈；依赖引入未留档。

问题必须是具体缺陷、回归、安全问题、违反已确认需求，或具有实际影响的可维护性问题。同一根因的重复表现合并为一个问题。证据不足时不报为缺陷，记入未验证内容。

## 6. 运行检查（固定规则）

查目标项目的检查脚本（如 `package.json` 的 `scripts` / `Makefile` / `pyproject.toml` 等）：含 `typecheck` 必跑（前提依赖已安装）；脚本缺失或依赖未装时记入「未验证内容」。不得发明命令、安装缺失工具或执行不存在的脚本。**不跑 lint**（评审不做 lint 检查，也不把 lint 结果写进报告）。

## 7. 输出（固定模板，禁止自创）

标准档必须逐字使用以下结构，轻量档使用其后轻量模板。禁止自创表格样式、emoji 等级标记、模板之外的结论段或维度。

总判定按固定映射给出，不做主观发挥：

- 存在 P0/P1 → 建议修复后再合入。
- 仅 P2/P3 → 可合入，P2 建议联调前处理。
- 无发现 → 可合入。

|---|---|---|

| C1 底线 | RC-02 | 同上 |
| C1 底线 | RC-03 | 同上 |
| C1 底线 | RC-04 | 同上 |

## 8. 自动交接（评审通过 → 生成提交消息）

- **触发**：总判定 = 可合入（含"无发现"与"仅 P2/P3"），且用户未明确表示"不用生成消息 / 不用交接"时，输出审查报告后**自动调用** `commit-msg` Skill 生成 Git 提交消息，无需用户再次发起。总判定 = 建议修复后再合入时不交接，只报告问题。
- **范围传递**：commit-msg 的 scope 与本次评审范围一致——用户指定了文件 / 提交范围则同范围；评审的是暂存区则 scope=staged（暂存区为空时由 commit-msg 自身规则回退更改区）。
- **边界**：该交接仅生成提交消息文本，不执行 `git add` / `git commit` / `git push`；commit-msg 的回退、风险提醒等约束以其自身 SKILL.md 为准。

## 完成检查

- 标准档：覆盖矩阵逐规则（RC-01–12、RC-M1–06）全给出判定，不适用项均有一行理由，无静默跳过；RC-12 重复度候选清单已完整枚举并留痕；轻量档：会咬人的检查项（C1 / C2 / 变更集自洽）已全部覆盖。
- 每个发现引用规则 ID；标准档严重度经两因子矩阵或 P0 直判，轻量档附一句话定级理由。
- 已先检查需求遗漏和范围扩大（C4），再检查代码质量。
- 机械扫描已跑完整个差异，并遵守"先裁决后求证"与"不得只因出现某模式就判问题"的标准。
- 耗时纪律合规：差异未重复拉取、结论未重复推导、交叉验证未超上限。
- 没有把无关既有问题归因于本次变更。
- 没有修改代码。
