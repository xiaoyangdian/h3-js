# 生成变更报告

## 职责

接收外部确定的权威变更范围，整理统一变更数据，再按指定模式输出：

- `handoff`：代码级完成交接。
- `markdown`：跨人员、跨会话或审计留档。
- `commit-message`：可直接使用的 Git 提交标题与正文。

本 Skill 不决定“哪些改动应该算进来”。范围由用户或调用 Rule 提供；Skill 只读取该范围、提取事实并按模式表达。

本 Skill 不实现功能、不修复问题、不执行完整 Review，也不运行 `git add`、`git commit` 或 `git push`。

## 调用协议

把输出形式和变更范围作为两个独立输入：

```yaml
mode: handoff | markdown | commit-message
scope:
  kind: task | staged | unstaged | files | commit-range
  include: []
  exclude: []
  baseline: 可选；task 或 files 模式需要时提供
  target: 可选；task、files 或 commit-range 需要时提供
```

### 权威范围来源

按以下优先级确定 `scope`：

1. 用户在当前请求中明确指定的范围。
2. 调用 Rule 或其他 Skill 显式传入的范围。
3. 两者都没有时，询问用户要使用本轮任务、暂存区、未暂存区、指定文件还是提交范围。

最新的用户明确指示可以修改之前的 include/exclude。范围一旦确定，在本次输出中保持一致，不因“这些代码不是本轮修改”而二次过滤。

### 范围类型

- `task`：调用方提供本轮任务开始基线、最终内容和实际触及文件。
- `staged`：完整暂存区差异，即 `HEAD → index`。
- `unstaged`：未暂存差异，即 `index → working tree`。
- `commit-range`：用户指定的提交、基线与目标之间的差异。
- `files`：用户指定文件；同时沿用或询问对应的比较来源。

用户已经说“根据暂存区生成 Git message”时，`mode=commit-message`、`scope.kind=staged` 已经完整，不再询问是不是只包含本轮任务。

## 范围约束

- 对 `staged`，默认包含所有已暂存文件和全部暂存差异，包括本轮任务开始前已经存在的改动。
- “不是本轮修改”“与当前需求无关”不能成为自动排除理由。
- 只有用户或调用方明确给出的 `exclude` 才能排除文件或差异。
- 用户说“暂存区排除 `A`”时，范围就是完整暂存区减去 `A`；其余内容进入同一输出。
- 多个文件属于不同功能时仍按权威范围生成一个完整结果；除非用户要求，否则不拆分消息或报告。
- 范围为空时直接说明没有可报告差异，不虚构内容。

## 建立统一变更数据

### 1. 读取范围差异

根据 `scope.kind` 使用对应比较：

| kind | 比较来源 |
|---|---|
| `task` | 调用方传入的任务开始基线 → 最终内容 |
| `staged` | `HEAD → index`，对应完整 cached diff |
| `unstaged` | `index → working tree` |
| `commit-range` | 用户指定 base → target |
| `files` | 指定文件 + 已确定的比较来源 |

不得把某一种比较来源的结果混入另一种范围。
每次调用都重新执行对应的差异读取命令获取实时差异；不得以会话开头的状态快照、对话历史或先前读取过的差异为前提——那些状态可能已经过时。

### 2. 拆分代码级变化

不输出独立的文件变更统计表。直接为每项代码变化记录：

| 字段 | 内容 |
|---|---|
| 操作 | 新增 / 修改 / 删除 / 重命名 |
| 文件 | 项目相对路径，不附行号 |
| 该项行数 | `+N / -N`；不可取得时如实说明 |
| 代码对象 | 函数、方法、组件、状态、常量、事件、模板节点、路由、配置键、接口等准确名称 |
| 具体逻辑 | 修改的是该对象中的哪个条件、分支、状态、调用、渲染或副作用 |
| 实现方式 | 复杂新增或修改的触发入口、处理顺序和影响 |

删除一个功能涉及多个函数、状态、模板节点和事件时分别列出，不用“全部相关逻辑”合并。

没有独立函数名时不虚构名称，使用稳定对象定位，例如 `GalleryView.render > sort comparator`、`template > #btnSortByName` 或 `GridView.init > click handler`。

行数以权威范围对应的 base 与 target 为准。多处不连续变化可以分别记录；同一差异行不能重复累计。无法可靠取得时写“不可可靠统计”，不估算。

### 3. 控制实现说明详略

以下新增或修改必须说明实现机制：

- 新函数、方法、组件、事件流程或调用链。
- 状态机、循环切换、条件分支、排序/过滤算法、异步时序或错误处理。
- 数据转换、本地存储、缓存、接口字段、兼容迁移或多步回退。
- 一个用户动作经过多个函数、状态或渲染阶段。

说明触发入口、关键状态或数据如何变化、主要分支顺序，以及最终如何影响界面或调用方。描述技术机制和设计结果，不输出模型内部思考过程。

单个默认值、字面量、枚举、文案、配置键、一对一重命名、直接删除、简单回退或复用已有函数，只写清事实即可。

## 输出模式

### `handoff`

按以下顺序输出：

1. 结果与用户可见行为。
2. 代码级变更清单。
3. 验证证据。
4. 未验证与风险。
5. 待确认事项（如有）。

代码级清单使用：

| 操作 | 文件 | 该项行数 | 代码对象 | 修改的具体逻辑 | 实现方式 |
|---|---|---:|---|---|---|

小改动可以压缩文字，但不能省略范围内文件、准确代码对象、行数、验证和未验证范围。

### `markdown`

只有用户明确要求留档、现有技术文档要求回写，或用户已经确认跨人员/跨会话交接时写文件。

- 内容沿用相同 `scope` 产生的统一变更数据。
- 写入用户指定路径；未指定且无法从项目约定确认时先询问。
- 不为小改动擅自创建文档。
- 最终回复仍提供摘要和文档路径。

### `commit-message`

从完整权威范围提炼一条可直接使用的 Git message：

1. `scope` 明确时立即读取对应差异，不再按任务来源筛选，也不再次询问范围。
2. `scope.kind=staged` 时分析全部暂存差异；只应用显式 `exclude`。
3. 标题必须使用 Conventional Commits 标头：`type(scope): summary`，其中 `type` 取自
   `feat` / `fix` / `docs` / `style` / `refactor` / `perf` / `test` / `build` / `ci` / `chore` / `revert`
   （纯文档/规则/Skill/配置类改动一般用 `chore` 或 `docs`；功能新增用 `feat`；缺陷修复用 `fix`）。
   不再沿用"无标头简洁标题"的旧风格，标头为必填项。
4. 标题概括整个范围的主要结果；正文覆盖范围内各项关键行为和代码对象。
5. 多个不同改动仍生成覆盖完整范围的一条消息，除非用户要求拆分。
6. 默认首先提供一个可复制的完整消息代码块，不要求用户再组合内容。
7. **验证行纪律**：有价值时在正文记录验证和未验证范围；只生成消息，不执行暂存、提交或推送。
8. **风险信号提醒**：读取差异时直接观察到明显风险信号（疑似误提交、敏感信息、超大二进制、破坏性删除）的，在消息代码块之外单独提醒用户，不写进消息正文；仓库状态或工作流建议（是否重新 add、暂存区与上次不同等）不属于风险提醒，不得附加。

如果用户明确排除某个文件，提交消息不得提及该文件；未排除内容不得因为与本轮任务无关而遗漏。

## 事实边界

- 权威范围回答“报告什么”，差异证据回答“发生了什么”；Skill 不重新定义范围。
- 只报告范围内差异能够证明的事实，不把预计文件或计划当作实际变化。
- 不因为报告需要而修改代码、格式化文件或补做未经授权的工作。
- 没有运行时证据时，不把 Lint、类型检查或静态阅读写成功能验证通过。
- 不判断疑似测试代码、错误代码、回归风险或提交风险；此类质量判断由 `review-change` 负责。唯一例外：`commit-message` 模式「风险信号提醒」条款——仅限读取差异时直接观察到的明显信号，只提醒不展开分析，不构成完整 Review。
