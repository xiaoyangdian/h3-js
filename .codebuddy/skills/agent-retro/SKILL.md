# AI 行为复盘

把真实任务中的可观察轨迹整理为可追溯的正向或负向案例，用于后续人工判断规范是否值得调整。本 Skill 是严格的用户专属工具，不是自动纠错、后台监控或会话结束钩子。

## 1. 严格触发边界

仅在以下任一条件成立时执行：

- 用户明确点名 `agent-retro`。
- 用户明确要求“复盘 / 记录 / 保存 / 沉淀这次 AI 行为”。

除此之外一律不触发：

- AI 自己认为做错、偏题、失败或表现很好。
- 用户普通纠正、提出异议、强烈反对、批评、表扬或给出正向反馈，但没有明确要求复盘或记录。
- Rule 或其他 Skill 判断本轮值得沉淀。
- 需求完成、Review 完成、会话即将结束或连续失败达到阈值。

AI、Rule 和其他 Skill 不得自动调用、顺带调用或主动建议用户调用本 Skill。不得配置后台采集、自动 Hook 或被动记录。

## 2. 确认复盘来源与范围

支持三种来源：

- `current-session`：当前可见会话及其工具、文件变化。
- `transcript-file`：用户指定的轨迹、问答或日志文件。
- `provided-content`：用户直接粘贴的片段。

优先采用用户指定的来源和范围。范围不清且会改变结论时，只询问一个最小必要问题。

只使用可观察证据：用户提示、可见回复、明确的 Rule/Skill 调用、工具调用及结果、文件差异、用户纠正与最终结果。不得声称读取隐藏思维链，不得根据语气臆测用户评价。

## 3. 获取用户评价

复盘开始前，必须取得下面三个字段：

1. 总体结论：`认可` 或 `不认可`。
2. 评分：`1–5` 分，其中 1 表示完全不符合预期，5 表示非常满意。
3. 复盘备注：用户希望重点分析的行为、问题、亮点或疑问；没有特别方向时可填写“无”。

推荐一次询问：

> 在开始复盘前，请提供三项信息：你总体认可还是不认可本轮结果、1–5 分评分，以及一条复盘备注。备注可以写希望重点分析的问题、做得好的地方或疑问；没有特别方向可写“无”。

如果用户在本次调用中已经明确给出某字段，不重复询问，只补齐缺失字段。用户可以给出看似不一致的结论和评分，不要擅自改写；仅当冲突会让案例类型无法确定时再确认一次。

把复盘备注作为分析方向和证据检索线索，优先回应用户点名的行为，但不能把备注中的原因猜测直接写成事实或唯一归因。备注为“无”时，根据认可结论、评分和可观察证据确定分析重点。

结论决定案例主类型：

- `认可`：优秀案例，重点提炼值得保留的行为。
- `不认可`：问题案例，重点定位期望与实际的偏差。

评分用于表达强度，不代替用户结论。不要把一次认可直接推广为通用最佳实践，也不要把一次不认可直接判定为 Rule 或 Skill 缺陷。

## 4. 收集最小充分证据

围绕用户评价提取：

- 原始目标、明确范围和完成标准。
- AI 实际采取的关键动作与顺序。
- 用户认可或不认可的具体行为，以及复盘备注指向的重点。
- 相关工具结果、文件差异和最终产物。
- 规范实际生效、未生效或无法证明的部分。
- 结果影响以及仍未验证的事实。

默认只记录脱敏后的证据摘要，不整段复制原始会话。口令、令牌、个人信息、内部地址及与结论无关的源码不得进入记录。引用外部轨迹时保留来源路径或标识，不复制源文件。

## 5. 分析案例

### 5.1 优秀案例

回答：

- 哪个具体行为获得认可？
- 它解决了什么真实问题？
- 哪些前提使该行为有效？
- 哪些行为值得保留，哪些部分没有足够证据推广？

### 5.2 问题案例

回答：

- 用户期望是什么，实际发生了什么？
- 偏差首次出现在哪个可观察步骤？
- 它造成了什么负担或风险？
- 最小可行的改进方向是什么？

### 5.3 归因

仅在证据支持时，从下列类别中选择一个主因和必要的次因：

- Rule 缺失、冲突或路由不当。
- Skill 触发边界或工作流说明不当。
- 平台没有加载或没有执行相关规范。
- 项目事实或用户信息不足。
- 模型、工具或执行过程没有遵循已存在的约束。
- 未发现规范缺陷，属于正向表现或偶发现象。

每个归因标注 `高 / 中 / 低` 置信度，并列出证据和可能的替代解释。没有证据时写“无法确认”，不为了得出结论而归咎规范。

## 6. 生成复盘草稿

读取并使用 `assets/retro-template.md`。仅保留与本案例有关的段落，在对话中先给出短摘要和完整草稿预览。

案例编号使用 `RETRO-YYYYMMDD-NN`；同一天无法确认已有编号时，可加简短时间或主题后缀，避免覆盖。

## 7. 保存权限

调用词决定本轮写入权限：

- 用户明确说“记录 / 保存 / 沉淀”：补齐评价后可以保存，不再重复询问是否保存。
- 用户只说“复盘 / 分析 / 看看原因”：只在对话中展示草稿；必须获得用户后续明确同意才可写文件。

保存位置按以下顺序确定：

1. 用户指定路径。
2. 项目根目录 `复盘记录/` 文件夹（单层不分月，文件名 `RETRO-YYYYMMDD-NN-<topic>.md`）。本仓库文档平铺在根目录（`交接文档.md` / `参考资料.md` / `简化玩法设计.md`），复盘记录单独成目录，不并入正文文档。
3. 项目根无法唯一确认时，先询问，不猜测。

文件名使用 `RETRO-YYYYMMDD-NN-<short-topic>.md`。创建新记录，不覆盖既有记录。反馈目录不是 Rule 或 Skill 的运行依赖，删除历史反馈不能破坏规范运行。

## 8. 修改权限

本 Skill 不得：

- 修改 Rule、Skill、代码或项目配置。
- 自动把案例转成回归测试、规则条款或模板。
- 因负面案例自动修复，或因正面案例自动扩大适用范围。

可以在记录中给出不超过 3 条候选改进，每条说明目标对象、证据、预期收益和副作用。用户后续明确要求实施时，将其视为新的修改任务；修改 Skill 时按所用 AI 编程工具的技能创建/编辑流程另行处理。

## 9. 完成检查

完成前确认：

- 本次由用户明确触发，而不是 AI 自判触发。
- 已获得 `认可 / 不认可`、`1–5` 分和复盘备注；用户没有特别方向时明确记录“无”。
- 案例类型与用户结论一致。
- 事实、推断、未知项分开陈述。
- 未暴露敏感信息或隐藏思维链。
- 未取得保存授权时没有写文件。
- 没有自动修改任何规范或代码。
