# 定位应用问题（填空表模式）

## 目的

定位应用故障，给出日志对照代码验证过的根因。先诊断，再决定是否修复。

不得实施产品修复、重构无关代码或自动调用其他 Skill。唯一允许的源码修改：为取证所必需的最小临时诊断改动（日志埋点与二分实验），取证后还原。

## 执行模式

排查的全部工作 = 填下面这张表。表填完或填不动的**当轮**，直接把表 + 取证请求回复用户。没有其他出口。

### 填空表

**空1 现象**

| 项 | 内容 |
|---|---|
| 实际看到（页面 / 接口 / 提示原文 / 数据值） | ____ |
| 期望正常（即用户想达成的效果） | ____ |

- 任一项缺失 → 第一轮回复只能是澄清提问，不得包含归因。
- 现象中的错误信号（状态码 / 报错文本）按字面含义解读（404 = 请求未到达目标处理层），顺着它定位链路，不得跳过直奔深层推测。
- 无法稳定复现时，先收集链路执行记录（现有日志、埋点输出），不直接猜修。

**空2 链路（找到多少填多少）**

从「用户操作 → 数据来源 → 判定逻辑 → 渲染 / 返回输出」逐步填，每步 = 文件 + 函数 + 关键判定条件：

- 入口：____
- 判定点（过滤 / 匹配 / 状态门槛 / 早退）：____
- 数据流转节点（原始值 → 转换后 → 输出用值）：____
- 输出 / 渲染点：____
- 【缺口】读不到的步骤：卡在 ____

定位手段：

- **文案溯源**：现象中的提示文案先在仓库全文 grep——是自家字符串 → 渲染点当场定位，归属当轮告知用户（顺链路讲清哪个组件哪个分支出的）；是接口返回的数据/文案 → 在对应服务项目里把返回链路查清楚再讲。仓库查不出归属才问用户，问"哪个页面 / 哪个位置"，不问"是不是我们的"。
- **基线溯源**：正常行为不明确时，先查 git 历史（log / blame / 关键 commit 的 diff）、代码注释和设计文档还原设计意图——某个过滤条件是哪次 commit 因什么原因加的，往往当场解释现象。
- **用户模型 diff**：用户口述过业务模型 / 接口逻辑（如"匹配上就显示"）记为「用户模型」；读代码发现实际判定条件多于或少于用户模型 → 当轮报告 diff，差异往往就是根因。
- 链路图当轮告知用户，用户可纠正。

部分完成合法：【缺口】本身就是交付内容——链路读到哪一步，就告诉用户到哪一步、断在哪。

**空3 日志覆盖（对应空2 每一步：已存在 / 补完）**

对空2 的每个步骤填一项：

- 现有日志已存在 → 标来源（console / network / 服务端日志 / git 历史）
- 现有日志不存在 → **当场补 [diag:xxx:stepN] 埋点**（自动补上，不问不等）

填完状态 = 空2 每一步都有日志点位。

埋点细则：

- 判定点打印判定条件的**完整字段值**（过滤条件逐字段 / 状态值 / 匹配双方实际值），只打「命中 / 未命中」布尔不合格。
- 唯一标记 `[diag:链路名:步骤号]`，只打对照执行流所需的值。
- 浏览器用 console；无浏览器环境的端用该环境标准输出或调试控制台。
- 「不命中 / 不生效 / 为空」类现象，必须同时找一个**正常样本**（别的窗口 / 数据 / 请求），两条路径日志并排 diff——单看故障侧只能看到「没命中」，并排才能看到差在哪个字段。

**空4 取证请求**

- 操作步骤（在哪个页面 / 接口做什么复现）：____
- 回贴内容（所有带 [diag:] 的日志行 + 紧邻报错；Web：DevTools Console，移动端：调试控制台 / vConsole，服务端：日志输出）：____
- 实验模式时（执行什么动作，回贴状态码 / 是否渲染 / 截图）：____

### 强制规则

1. **表内没有「分析可能原因」的空。** 推演无处落笔。「断点在哪一步」不在表内——它只能由用户回贴的日志填，AI 自己填不了，所以流程必然终止于输出取证请求。
2. **每空前进的唯一方式是新事实**：读到新代码行 / 新日志行 / 新用户输入。同一空无新事实重推 = 空转 → 立即停止填表，直接输出。
3. 填完或填不动 → 当轮直接回复：已填的表 + 【缺口】+ 空4 取证请求。
4. **修复方案不属于任何一空。** 表内出现修复方案设计即违规——根因未定位前的方案 = 无证据推断。
5. 回贴证据之前，输出只能是填空表现状 + 取证请求，不是结论。不得输出"应该是 / 大概率是"式归因。
6. **禁止思考（`02-redlines`「禁止思考」，最高优先级）**：本技能全程不做推理性展开——不列"可能原因 1/2/3"、不建假设链、不分析时间线、不为已经读到的代码结论再找验证。判定条件读到了就**原文陈述**（条件原文 + 触发链 + 谁赋值 / 谁清空），答完即停。用户说"直接告诉我 X""不要推测，告诉我链路"时，**指令即方法**，只给原文链路，不加推理铺垫。判据：**这段推演的答案会不会改变下一步动作？** 不会 → 不想也不写（用户原话："你好像还在推测……这为什么需要推测？"，333 事故定为违规样板）。

## 本项目取证手段（HeroWO）

现象落地成这三种，取证物固定：

| 现象 | 取证物（本来就是日志点位） | 怎么拿 |
|---|---|---|
| 探针跑不过 | 该套件 FAIL 行的「期望 / 实际 / 前置条件」 | `node battle-ui/_probeN.js`；断言输出本身就是取证件 |
| 浏览器里不显示 / 点了没反应 | `console.log` 埋点 | 在 `onHexClick` → `computeOptions` / `approachOptions` / `damagePreview` → `performAttack` → `doAttack` → `render` 链上补 `[diag:xxx:stepN]`，请用户回贴 DevTools Console |
| 数值不对（伤害 / 命中 / 预览与实际不符） | 中间量单步打印 | 探针已把 `calcDamage` / `dmgMult` / `rollDamage` / `effDef` 挂在 `__T`；直接打印各乘子项（I1/I4/I5/R1/R5）比打印最终值有用 |

补充纪律：

- **改代码后先跑基线再谈现象**：全套 17 套 687 项是环境自检；只在 `_probe` 里补一行打印就断言"代码失效"属未取证。
- **规则类现象先查出处**：`参考资料.md` §2 与 `Core/` 原文能直接回答的（"原版是不是这样算"），属于查证不属于推理，先查再问。
- **数值差异必须给两侧原值**：期望值来源（`参考资料.md` 哪一节 / 哪套断言）+ 实际值（探针或 console 输出），不给出处不给数。

## 验证循环（回贴后）

用户回贴 → 对照空2 链路逐点核对执行流：

- 某步骤执行流与代码不符 → **断点定位**（断点处不满足的条件 + 完整字段值就是根因），输出结论（用下方模板）。
- 执行流完全相符但现象仍异常 → 链路图不全：补空2 缺口、补空3 埋点（上轮实验改动必须已还原），再次输出取证请求——不是开始猜原因。
- 单个矛盾取证 1 次仍未定位断点，或链路补完仍有未覆盖分支 → 停止，报告现状请用户裁决（`02-redlines`「排查铁律·单矛盾单取证」）。
- 用户粘贴的日志含敏感信息：不复述、不存档该部分。

## 二分实验（可选加速段）

链路过长或埋点成本过高时，在链路切一刀，把「断点在切刀上游还是下游」一刀定一半。允许改变控制流（mock 返回值 / 条件分支 / 早退 / 替换目标）。

- **替换法**：可疑目标换成 100% 能工作的已知良好替代物。例：接口请求失败——先换确定能通的端点，验证发送方（请求构造 / 鉴权 / 网络）没问题，再换回目标接口，问题即在目标一侧。
- **对照法**：可疑位置放一个确定能正常工作的对照物。例：组件失效——原位置加极简确定能渲染的组件；显示 = 宿主环境正常问题在原组件，不显示 = 环境有问题。
- **最小环境隔离**：可疑组件 / 模块拉到独立最轻量环境单独验证本体。
- **增量组合**：验证通过后逐步加回变量，每次只加一个。

实验纪律：

- **一轮只切一个变量**（埋点纯观察可并行，实验改变行为必须串行）。
- 每轮实验结束立即还原，再进行下一轮——实验改动叠加会污染现场和归因。
- 实验是诊断不是修复，取证后一律还原。
- 替换物 / mock 数据不使用真实凭证与个人信息。

## 既有纪律（不变）

- **先问后断**：把问题归因于用户侧原因（看错页面 / 别人的提示 / 缓存 / 旧环境）必须先出示凭据——版本凭据（可复制的构建号 / commit hash 且与本地比对）、UI / 网络凭据（截图 / 状态码 / 控制台报错）或代码凭据（git 状态证明该环境不含改动）；无凭据一律按当前代码的真实行为排查。
- **字面现象不是结论**：日志显示「未命中 / 为空 / 被过滤」时，「这不就没命中吗」不构成结论；必须继续回答两问——哪个条件不满足（打印判定输入的完整字段值）＋命中路径长什么样（有对照样本证明正常路径存在）。
- **发现即报告**：排查中读到的任何与现象相关的判定条件 / 状态门槛（如「状态 ≠ 进行中则不显示」），当轮原样告知用户，不得私藏在推理中——第一轮就能发现的东西拖到最后，用户白走多轮。
- **内部疑问必须出口**：诊断中产生的关于用户意图的疑问，当轮转化为对用户的提问，不得自行替用户回答。
- **禁止编造性 workaround**：根因未定位前，严禁用伪造数据（随机 id / 镜像数据 / 硬塞假值）强行制造「符合期望的表象」——它用假数据掩盖真问题。代码实际判定逻辑与用户模型不一致时，报告差异本身。

## 结论输出

仅在回贴证据与代码逐点对照完成、断点定位后输出：

```markdown
## 诊断结论
- 现象与复现：
- 根因（链路断点：哪一步、哪个判定条件、哪个字段值）：
- 用户模型 vs 代码实际行为的差异（若存在，写明差异内容；无则写"一致"）：
- 已核对无异常的链路点（证明断点不在这些位置）：

## 证据
1. `[diag:xxx:stepN]` 日志片段（用户回贴）→ 该步骤执行流与代码对照结果
2. 实验观察（如：替换端点后请求 200）→ 说明

## 临时改动
- 已清理：
- 仍保留：无 / 具体位置与清理步骤

## 建议下一步
- 最小修复方向、仍需补充的证据或外部责任方。
```

证据完成后才能建议修复方向，但不得直接实施。

诊断结束（定位或停止）后清理所有埋点与实验改动。等待用户复现期间，每轮取证请求列出全部保留位置。

## 完成检查

- 填空表每空有产出或明确【缺口】，无推演性内容混入。
- 每个结论都有用户回贴的日志 / 实验证据与代码逐点对照支持，没有凭代码阅读推断输出的结论。
- 没有输出过"应该是 / 大概率是"式未验证归因。
- 没有实施产品修复或范围外变更。
- 临时埋点与实验改动已全部还原或明确列出。
- 没有记录敏感信息（含用户回贴日志与实验数据中的敏感字段）。
